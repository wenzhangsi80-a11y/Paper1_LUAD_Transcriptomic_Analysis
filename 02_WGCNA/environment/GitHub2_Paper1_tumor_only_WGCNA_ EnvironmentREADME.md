# Computational Environment — Tumor-Only WGCNA

## 1. Overview

This document describes the computational environment, software dependencies, project path management, and reproducibility requirements for the ten-script tumor-only weighted gene co-expression network analysis (WGCNA) workflow in Paper 1.

The workflow covers:

- TCGA-LUAD primary tumor cohort reconstruction and expression-data preparation.
- WGCNA network construction and module detection.
- Clinical and survival analyses.
- ESTIMATE-based tumor microenvironment (TME) scoring and module–TME association analysis.
- Candidate-gene integration and WGCNA result auditing.
- Supplementary figure and table generation.
- Workspace recovery and reproducibility archiving.

The software environment varies according to the analytical requirements of individual scripts. Package versions and runtime information should therefore be obtained from the actual execution records rather than inferred from this document.

## 4. Workflow-Specific Software Requirements

Some analysis stages require specialized software beyond the general dependencies listed above.

### 4.1 Gene Annotation

`AnnotationDbi` and `org.Hs.eg.db` are used for supplementary human gene annotation and identifier mapping.

The preprocessing and integration workflows also use GENCODE human release 22 reference information for Ensembl gene-identifier and annotation-provenance checks.

The GENCODE v22 reference is an annotation resource and should not be treated as an R package dependency.

### 4.2 WGCNA

The `WGCNA` package is required for network construction and module-related operations.

Relevant functions include:

- `goodSamplesGenes()`
- Soft-threshold selection and network construction functions.
- Module detection and eigengene calculations.
- `moduleEigengenes()`

The preprocessing workflow uses `goodSamplesGenes()` for input quality assessment; network construction is performed in the subsequent network-analysis workflow.

Some later scripts use previously generated WGCNA objects rather than reconstructing the network. Their software requirements should be interpreted in the context of the functions actually called by each script.

### 4.3 Survival Analysis

The `survival` package supports the clinical and survival-analysis workflows, including:

- Conventional Cox proportional hazards regression.
- Schoenfeld residual diagnostics.
- Proportional-hazards assessment.
- Time-dependent Cox regression.
- Model comparison and time-specific hazard-ratio estimation.

The Cox models documented in the relevant workflows use Efron handling of tied event times where specified.

`survminer` is included as an additional survival-analysis and visualization dependency where required by the corresponding script.

### 4.4 ESTIMATE and TME Scoring

The ESTIMATE workflow uses an ESTIMATE implementation for common-gene filtering and TME scoring.

The reviewed script documents an installation source at:

`https://github.com/Moonerss/ESTIMATE`

The workflow uses functions including:

- `filterCommonGenes()`
- `estimateScore()`
- `plotPurity()`

The package name and installed version should be verified in the actual R environment. The script documentation contains both `estimate` and `ESTIMATE` references; these names should not be treated as interchangeable without checking the installed package and the functions used during execution.

The `remotes` and `BiocManager` packages are used for installation support or environment inspection where specified.

### 4.5 Supplementary Figure Generation

The final supplementary-figure workflow uses:

- `ggplot2` for figure construction.
- Arial as the specified plotting font.
- Cairo PDF output for designated final supplementary figures.

On Windows, the Arial font directory should be resolved through the system environment rather than a computer-specific absolute path.

Cairo output is a graphics-device requirement for the designated PDF workflow. It should not be interpreted as a requirement for every figure generated by the ten scripts.

## 5. Project Path Management

The analysis scripts use project-root-relative paths to improve portability and reproducibility.

The `here` package is used to identify the project root:

```r
project_root <- here::here()

input_dir <- file.path(
  project_root,
  "data"
)

result_dir <- file.path(
  project_root,
  "results"
)

figure_dir <- file.path(
  project_root,
  "figures"
)
```

Script-specific paths should be constructed using `file.path()` and the relevant project directory variables.

General path-management principles include:

- Avoid computer-specific absolute paths.
- Do not rely on manually setting the working directory using `setwd()`.
- Keep input data, generated results, and figures in their designated project directories.
- Preserve the distinction between `results/`, which stores generated analysis files, and `Results/`, which may contain documentation.
- Ensure that the repository is opened from the project root so that `here::here()` resolves the expected directory structure.

## 7. Package Installation and Version Recording

The analysis scripts check for required packages where specified. Package installation is generally managed separately from the analytical workflow.

Automatic package installation or updating should not be assumed to occur during script execution.

For reproducibility:

1. Install the required CRAN and Bioconductor packages in the R environment before running the relevant workflow.
2. Verify package availability and compatibility.
3. Record the exact R version and installed package versions.
4. Retain the runtime `sessionInfo()` output.
5. Preserve workflow-specific software-version records with the corresponding analysis outputs.

The following commands can be used for a focused package inventory:

```r
packageVersion("here")

packageVersion("survival")
packageVersion("ggplot2")

```

Additional package versions should be recorded according to the dependencies of the individual script.

The exact versions should be obtained from the actual execution environment. A version should not be retrospectively inferred from a current installation if the version used during the original analysis was not recorded.

## 9. Reproducibility and Execution Requirements

The following practices apply across the WGCNA workflows:

1. **Project-relative paths:** Use `here::here()` and `file.path()` for project path management.
2. **Read-only original inputs:** Preserve original expression, clinical, and annotation files.
3. **Explicit data interfaces:** Verify sample identifiers, gene identifiers, matrix dimensions, sample order, and required objects at workflow boundaries.
4. **Checkpoint preservation:** Save important intermediate and final objects using explicit RDS or RData checkpoints.
5. **Runtime environment records:** Retain R version, package versions, operating-system information, and `sessionInfo()` where available.
6. **No unverified package versions:** Do not infer historical package versions from a different R installation.
7. **No undocumented sample exclusion:** Descriptive PCA, clustering, connectivity, and expression-distribution results should not automatically trigger sample removal.
8. **Distinction between analysis and audit:** Document whether a workflow performs new statistical calculations, retrieves existing locked results, conducts descriptive audits, or recovers archived objects.
9. **Upstream checkpoint verification:** Confirm that required input files and R objects are available before running downstream workflows.
10. **Font and graphics consistency:** Use the font and graphics-device settings specified by the corresponding figure-generation script.
